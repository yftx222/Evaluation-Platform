# Trace 凭证、安全与留存

1. Worker 在领取 ADAPTER 租约、获得 Target 许可后，按冻结项目版本与 EVAL_TRACE_TARGET_VERSIONS 白名单决定是否签发。生产目标必须使用 HTTPS；开发仅额外允许数字回环地址的 HTTP。令牌由 attempt UUID 与 256 位随机秘密组成，库内保存 SHA-256 校验值。Trace ID 是公开定位符，读取仍需项目权限。
2. 接收方在读入请求体前验证凭证，解析与校验在写事务外完成。写事务按 Run、Case、Attempt、Trace 顺序加锁并再次比对摘要、所属 Run/Project、Attempt 阶段与状态、持有人、epoch、Run 状态和数据库时钟。写事务结束时复核截止时间。租约、Case 截止和签发后 5 分钟三者共同限制写窗口。暂停、取消、结束、丢失租约均阻止后续上传。
3. 生产回调要求请求 scheme 为 HTTPS。代理终止 TLS 时仅信任部署方控制的代理转发信息。明文令牌只出现在本次出站调用的专用请求头和回调的 Authorization 头。API 不回显原文、校验值和原始校验错误。收集服务、反向代理、业务服务均应关闭敏感头记录。已有 Worker 的响应回显检查在写预测与对端请求号前生效。
4. 客户端只提交获准保存的摘要与业务引用。服务端递归检查字段名及文本，拒绝常见认证头、密钥、Token、邮箱、手机号等可识别模式；使用字段级拒绝有助于调用方定位有问题的事件。自由文本仍需由来源端脱敏。input_tokens 等普通用量计数可以保存。
5. EVAL_TRACE_RETENTION_DAYS 为可选的正整数，默认 null。摘要的 archive_eligible_at 根据封口时间和当前配置计算。该时间供归档筛选，平台本阶段不会自动删除数据。保留天数由部署方结合存储增长、合规要求和归档演练决定。启用清理前需在隔离库恢复，核对轨迹数、顺序、内容、引用和权限。
6. 升级时先完成在途工作再应用 Alembic 0008_attempt_traces。新 Worker 启动时检查最低版本。历史尝试的空 trace_id 保留，避免给以前的评测虚构采集结果。在已有 Trace 数据的库上，迁移拒绝执行会丢失历史的降级；恢复到升级前需使用核验过的备份并处理升级后的新增数据。

## 4.3 归档标记和证据读取

经过部署方归档核验的已封口 Trace 可登记在 trace_archives。标记生效后，项目授权读取事件返回 410 TRACE_ARCHIVED，历史评分的事件引用返回 EVIDENCE_UNAVAILABLE / SOURCE_ARCHIVED 并保留事件编号。归档登记不修改 Score 或 Trace 的终态，恢复在线读取应先核对恢复的数据与原件再解除登记。运维人员负责登记与恢复。适用权限、摘要脱敏和外部登记来源见 [评分证据](evidence-model.md)。

## 4.4 验收库恢复演练

在专用 Compose PostgreSQL 中对合成客服评测的临时库执行 pg_dump -Fc，向新建空库执行事务性 pg_restore。用原组织成员和无权限用户验证报告、Trace 摘要、事件列表、逐事件详情和 Evidence。只在已核对相等的恢复副本上设置归档标记，确认 410 与 SOURCE_ARCHIVED，然后解除标记并逐项复核。演练使用临时文件与临时库；没有清除项目热数据。实际部署的备份加密、异地介质、恢复时间目标和留存天数仍需由部署方确定。
